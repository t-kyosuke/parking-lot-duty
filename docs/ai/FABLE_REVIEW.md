## 1. プロジェクト概要

吹田ラグビースクール（SRS）中学3年コーチ陣の「駐車場・ビデオ・カゴ当番」を自動割り当てするWebアプリ。
操作者は管理者（塚原さん）1人。コーチ陣はLINEで共有されたURLから閲覧のみ。
毎月末：調整さんCSVをアップロード → 出欠確認 → 自動割り当て → LINEにコピペ → 「公開する」でスマホ向けデータ更新。

## 2. アーキテクチャ概要（事実）

- React 19 + TypeScript + Vite 8。バックエンドなし。テストは Vitest（30件・性質ベース）
- **ロジックとUIが明確に分離**されている：
  - `src/lib/assignParking.ts` … 割り当てアルゴリズム（純粋関数のみ・テスト対象）
  - `src/lib/parseCsv.ts` … 調整さんCSVパーサー（純粋関数だが**テストなし**）
  - `src/lib/storage.ts` … localStorage 永続化＋GitHub公開API＋マイグレーション（**テストなし**）
  - `src/components/` … 画面10個（閲覧/ログイン/管理/CSV/出欠/結果/LINE/累計/設定/ヘッダー）
- データは2系統：管理者PCの localStorage が正、そこから「公開する」で `data.json` を
  gh-pages ブランチへコミットし、他端末は raw.githubusercontent.com から読む
- アプリ本体は main への push → GitHub Actions で自動ビルド・デプロイ（Pages ソースは Actions）

## 3. 良い点

- **アルゴリズムが純粋関数で、性質ベーステスト30件＋1年公平性シミュレーションで守られている**。
  この規模の個人プロジェクトとしては非常に手堅い
- カゴ連鎖を「駐車場/ビデオ確定後に読むだけの一方通行」にした設計判断が良い。
  公平性の核心（駐車場/ビデオ）に副作用が及ばない構造が型と実装の両方で保証されている
- 旧データ形式への後方互換（`computeKagoTakeHome` のフォールバック、`isKagoCounted` の互換扱い、
  マイグレーションの完了フラグ）が一貫して考慮されている
- 「変更前スナップショット＋git tag で復元ポイントを作ってから触る」文化が定着している
  （`docs/SPEC-SNAPSHOT-before-saturday-kago.md`、tag `pre-saturday-kago`）
- PROGRESS.md にセッションごとの変更・検証・エラーが詳細に残っており、履歴の追跡性が高い

## 4. 懸念点・リスク（重要なものだけ）

### 4-1. ドキュメントと実装の乖離【事実・今回修正済み】
- 旧CLAUDE.md に「除外コーチは設定画面で編集可能」とあったが、**設定画面にコーチ編集UIは存在しない**。
  コーチ名簿（3つの ORDER 配列と除外リスト）は `src/lib/constants.ts` に直書きで、変更にはコード修正＋デプロイが必要。
  `storage.ts` の `CoachConfig` 系関数はどのUIからも呼ばれていない（grepで確認済みの死にコード。export/import 互換のみ）。
  → 将来のAIセッションが「設定画面を探す」無駄をするので、CLAUDE.md / SPEC.md を実態に合わせて修正した。

### 4-2. CSVパーサーの静かな誤動作リスク【事実（コード上）／発生は未観測】
`src/lib/parseCsv.ts` は素朴な `split(',')` でパースしており：
- **クォート付きセルに非対応**。日程ラベルにカンマが入る（例：「4/26(日) 試合,雨天中止」）と
  その行の列が1つズレ、**出欠が別のコーチのものとして静かに取り込まれる**（エラーにならない）
- `〇`（漢数字ゼロ U+3007）は◯と認識されず△扱い → そのコーチが候補から静かに外れる
- 推測：調整さんの標準出力ではラベルにカンマが入ることは稀で、過去15か月で実害は出ていない。
  ただし「エラーにならず結果が誤る」種類のバグなので、防御（列数チェック or クォート対応）の価値は高い

### 4-3. テストの空白地帯【事実】
- `parseCsv.ts`：テスト0件。入力の入口で最も壊れやすい箇所（エンコーディング判定・ヘッダー探索・列マッピング）
- `storage.ts`：テスト0件。特に `getCountsForAssignment`（二重カウント防止）と
  `getPreviousKagoSession`（月またぎ引き継ぎ・新旧フォーマット判定）は割り当ての正しさに直結するロジック
- アルゴリズム本体（30件）との落差が大きい

### 4-4. 年度の崖【事実：コードが2026年度固定】
- `DEFAULT_SCHEDULE`（constants.ts）は2026年度の日付・曜日に固定。閲覧画面の「2026年度」表記もハードコード
- 月データは「4月」等の月名キーで年を持たないため、**2027年4月に前年4月のデータがそのまま「今の4月」として表示される**
- 対応は難しくない（年度更新手順の確立）が、**2027年3月までに計画的に**やる必要がある

### 4-5. セキュリティ（脅威モデル相応だが記録しておく）【事実】
- 管理者パスワードはブラウザ内判定のみ・localStorage に平文。ただし突破しても得られるのは
  「自分のブラウザ内のデータ編集」だけで、公開の実権限は GitHub トークンを持つ管理者PCにしかない → 許容範囲
- **GitHub トークンが管理者PCの localStorage に平文**。XSS面は React の標準エスケープで狭いが、
  トークン自体を Fine-grained（parking-lot-duty リポジトリの Contents:write のみ）にして被害半径を絞るのが安価で効果的
- **エクスポートJSONに管理者パスワードが平文で含まれる**（トークンは含まれない）。
  エクスポートファイルを誰かに渡すとパスワードも渡る点は運用上知っておくべき
- `data.json`（コーチ名＋出欠＋当番）は公開リポジトリ経由で誰でも読める。
  推測：LINEでURL共有している運用上、了解済みの公開情報と考えられる（要・本人確認1回）

### 4-6. 二重データ源の運用リスク【事実（設計どおり）】
- 閲覧画面は「ローカルデータがあればローカル優先」。管理者が割り当て後に**「公開する」を忘れると、
  管理者のPCだけ最新でコーチのスマホは古いまま**になる。エラーは出ない
- また、コーチが自分の端末で管理者ログインして操作すると、その端末はローカルデータを持ってしまい
  以後リモートを読まなくなる（全データリセットで復旧）。パスワードが広まると起こり得る

### 4-7. 軽微（まとめ）【事実】
- lint 9件：全角スペース4件（LINE整形のため**意図的・直さない**）、`App.tsx:22` の setState-in-effect 1件、
  useMemo 依存の警告3件、未使用 eslint-disable 1件。動作への実害は現状なし
- `public/data.json` はリポジトリに残っているが本番の閲覧では読まれない（読み元は gh-pages ブランチの raw URL）。
  紛らわしいので扱いを明確化したい
- 管理画面の対象月が常に「4月」始まり（当月が初期選択されない）
- CI の Node 20 は GitHub 側で非推奨警告（実害なし・任意でバンプ）

### 4-8. 累計の手動調整が次の割り当てで消える【事実・2026-07-03 追加発見】
- 設定画面の±調整は、次に「当番を決定する」を押した時点の `recalculateCumulativeCounts`
  （確定済み全月からの再計算）で上書きされて消える。**調整は直後の1回の割り当てにしか効かない**
- そのため UI・ドキュメントが約束する「新コーチに平均をセット」「善意の実績を反映」は恒久的には機能せず、
  年度更新で累計を手入力で引き継ぐことも不可能
- 対応：NEXT_ACTIONS **A-4**（繰越機能の導入）で恒久化する計画（2027年1月まで）

## 5. AIが今後作業する上での注意点

1. **最初に PROGRESS.md → CLAUDE.md → docs/ai/SPEC.md の順で読む**。仕様の正はこの3つ
2. **駐車場/ビデオの公平性ロジック（`assignDuties`/`pickByCount`）は聖域**。カゴ関連の変更で触らない
   （一方通行の原則）。アルゴリズムを変えるときは必ず「現仕様スナップショット＋git tag」を先に作る
3. `import type` 必須（tsconfig の `verbatimModuleSyntax: true`。忘れるとビルドが落ちる）
4. `LineAnnouncement.tsx` の全角スペースは意図的。lint エラーだが「修正」しないこと（LINEの見栄えが崩れる）
5. コーチ名簿の変更は `constants.ts` 直接編集（設定画面にはない）。過去の確定済み月データは書き換えない
6. ブラウザ検証で localStorage にテストデータを流し込むときは、先にアプリURLへ移動し、
   `srs_migration_remove_hayashi_v1='done'` を立ててから（さもないと5月以降が消える）
7. worktree で `index.lock` エラーが出たら、git が表示する**絶対パス**のロックファイルを消す（既知事象）
8. 本番デプロイ（main への push）は**塚原さんのGOを得てから**

## 6. サブエージェントを使うべき場面／使わない場面

- **使わない（メインが直接やる）**：全体レビュー、設計判断、優先順位付け、アルゴリズム変更、最終確認。
  このリポジトリは全ソース合わせて4千行弱で、メインが直接読める規模
- **使ってよい（自己完結した調査のみ・軽量モデル・単発）**：
  - 実データCSV（大きいもの）の中身検証やログの要点抽出
  - テストが落ちたときの原因切り分け（再現ログの収集）
  - 特定観点だけの限定調査（例：XSS面の総当たりチェック）
